CAMBIO 1 — ejecutar las tool calls de Haiku en paralelo, no secuencial
═══════════════════════════════════════════════════════════════

CAUSA RAÍZ:
Cuando Claude (Haiku) devuelve varias `tool_use` en un mismo turno — por ejemplo, tres llamadas a `deep_search` con preguntas distintas — el backend las ejecuta con un `for` que hace `await executeChatTool(...)` una por una. Aunque Haiku pida las tres juntas, el servidor las sirve en serie. Esto anula cualquier beneficio de que Haiku decida paralelizar su propia búsqueda: no importa cuántas tool calls pida a la vez, el tiempo total es la suma de todas, no el máximo.

UBICACIÓN: función `runHaikuTier`, dentro del loop principal, justo después de `const toolUses = data.content.filter(...)`.

Buscá este bloque exacto:

```
    const toolResults: any[] = [];
    for (const tool of toolUses) {
      const resultText = await executeChatTool(tool.name, tool.input, repo, send, sessionId);
      toolResults.push({ type: 'tool_result', tool_use_id: tool.id, content: resultText });
      // Track whether any tool call returned real content (not an error or empty result)
      if (
        (tool.name === 'grep_code' || tool.name === 'read_file' || tool.name === 'list_files') &&
        !resultText.startsWith('Sin resultados') &&
        !resultText.startsWith('Error:') &&
        resultText.trim().length > 50
      ) {
        foundFiles = true;
      }
      // Cambio 1 — update consecutive-shallow-search counter
      if (tool.name === 'grep_code' || tool.name === 'read_file') {
        consecutiveShallowSearches++;
      } else if (tool.name === 'deep_search' || tool.name === 'task_complete') {
        consecutiveShallowSearches = 0;
      }
    }
```

Reemplazalo por (ejecuta todas las tool calls del turno con `Promise.all`, y después procesa los resultados en el mismo orden — la lógica de `foundFiles` y `consecutiveShallowSearches` queda idéntica, solo cambia CÓMO se obtienen los `resultText`):

```

      toolUses.map(async (tool) => ({
        tool,
        resultText: await executeChatTool(tool.name, tool.input, repo, send, sessionId),
      })),

    const toolResults: any[] = [];
    for (const { tool, resultText } of toolExecutions) {
      toolResults.push({ type: 'tool_result', tool_use_id: tool.id, content: resultText });
      // Track whether any tool call returned real content (not an error or empty result)
      if (
        (tool.name === 'grep_code' || tool.name === 'read_file' || tool.name === 'list_files') &&
        !resultText.startsWith('Sin resultados') &&
        !resultText.startsWith('Error:') &&
        resultText.trim().length > 50
      ) {
        foundFiles = true;
      }
      // Cambio 1 — update consecutive-shallow-search counter
      if (tool.name === 'grep_code' || tool.name === 'read_file') {
        consecutiveShallowSearches++;
      } else if (tool.name === 'deep_search' || tool.name === 'task_complete') {
        consecutiveShallowSearches = 0;
      }
    }
```

EFECTO SECUNDARIO ESPERADO (no es un bug, avisale al usuario si lo ve):
Los mensajes `send('action', ...)` que cada `deep_search`/`grep_code` emite mientras busca pueden llegar entreverados en el log — por ejemplo, ver "🔎 Paso 1" de una búsqueda intercalado con "📌 Evidencia leída" de otra. Es cosmético, no afecta el resultado final ni el orden de los `tool_result` que le vuelven a Claude.

CAMBIO 2 — Haiku reintenta con múltiples deep_search separados,
no una sola query combinada
═══════════════════════════════════════════════════════════════

CAUSA RAÍZ:
Hoy, cuando Haiku genera variantes de dominio para buscar un concepto, las combina TODAS en una sola llamada a `deep_search` con `|` (ej. `deep_search(query: "trailingStop|TRAILING_STOP|trailing_stop|callbackRatio")`). Eso internamente arma un solo patrón regex — es una búsqueda, no varias. Si esa única búsqueda combinada no encuentra evidencia suficiente, el prompt no le dice a Haiku que separe esas variantes en llamadas independientes — y aunque lo hiciera, antes del Cambio 1 esas llamadas se hubieran ejecutado igual de secuencial.

Con el Cambio 1 ya aplicado, el backend SÍ puede correr varias `deep_search` en paralelo dentro del mismo turno — pero hace falta decírselo a Haiku explícitamente en su prompt, porque hoy no tiene ninguna instrucción que lo empuje a separar variantes en tool calls distintas.

UBICACIÓN: constante `HAIKU_SEARCH_SYSTEM`, en la sección "VARIANTES DE DOMINIO".

Buscá este bloque exacto:

```
VARIANTES DE DOMINIO — generá 3-5 antes de llamar a deep_search, NO buscás el término literal:
   - camelCase (ej: "trailing stop" → trailingStop)
   - CONSTANT_CASE (ej: TRAILING_STOP_ENABLED)
   - snake_case (ej: trailing_stop)
   - Jerga del dominio si aplica (en trading: callbackRatio, rangeRate, movingPlan)
   - Sinónimos funcionales cortos (ej: "SL móvil")
  Pasalas todas juntas: deep_search(query: "trailingStop|TRAILING_STOP|trailing_stop|callbackRatio")
```

Reemplazalo por (agrega un párrafo nuevo de instrucción para el caso de reintento; no toca la instrucción original del primer intento):

```

   - camelCase (ej: "trailing stop" → trailingStop)

   - snake_case (ej: trailing_stop)
   - Jerga del dominio si aplica (en trading: callbackRatio, rangeRate, movingPlan)
   - Sinónimos funcionales cortos (ej: "SL móvil")
  Pasalas todas juntas en tu PRIMER intento: deep_search(query: "trailingStop|TRAILING_STOP|trailing_stop|callbackRatio")

REINTENTO EN PARALELO — si ese primer deep_search (con las variantes combinadas) vuelve con \
evidencia insuficiente o vacía, NO repitas un segundo deep_search con más variantes combinadas \

distintas, no una combinada.
```
